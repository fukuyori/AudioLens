# M1: エンジン検証メモ

- 版数: 0.1
- 作成日: 2026-08-03
- 対象: `src/engine/`、`src/tools/passthrough/`、`src/tools/tone/`

M1 の目的は「キャプチャ → パススルー → 再生」を実装し、遅延とグリッチを実測することである。DSP は入っていない(`IAudioProcessor` のフックのみ用意)。

---

## 1. 構成

```
audiolens_passthrough   検証用 CLI。取り込み → (DSP フック) → 再生
audiolens_tone          信号発生 CLI。指定デバイスへ正弦波を出力
audiolens_tests         オフライン単体テスト(ハードウェア不要)
```

エンジンは 2 スレッド構成である。

| スレッド | 処理 |
|---|---|
| キャプチャ | WASAPI イベント待ち → float32 へ変換 → **DSP** → リングバッファへ書き込み |
| 再生 | WASAPI イベント待ち → リングから読み出し → ドリフト補正 → デバイス形式へ変換 |

DSP をキャプチャ側に置いたのは、取り込んだフレームをそのままの数だけ処理でき、後述のドリフト補正によるフレーム削除・挿入が DSP の内部状態に影響しないためである。

## 2. クロックドリフトの扱い

取り込み元と出力先は別デバイスであり、別のクロックで動く。放置するとリングバッファは必ず枯渇するか溢れる。

現在の対策は、再生スレッドがリング充填量を監視し、目標値(リング容量の 1/2)からデッドバンド(キャプチャ周期の 1/4)を超えて外れたときに **1 コールバックあたり 1 フレームだけ** 削除または複製するというものである。

- 補正能力は毎秒 100 フレーム弱、48 kHz 換算で 2000 ppm 以上。実機のクロック差(通常 100 ppm 未満)に対して十分な余裕がある。
- 1 フレームの削除・複製は聴感上分からない。
- M2 以降でアダプティブリサンプラーに置き換える予定(`docs/architecture.md` §8)。

## 3. ループバックが無音のときの挙動

ループバックでタップしている再生デバイスに何も再生されていないと、WASAPI はパケットを 1 つも配送しない。イベントも発火しない。このとき再生側は供給が途絶えて underrun し続ける。

対策として、キャプチャスレッドは待機にタイムアウトを設け、**2 回連続でパケットが来なかった場合のみ** リングを目標値まで無音で埋める。

- 2 回連続という条件により、再生中の一瞬の隙間に無音が挿入されることを防いでいる。
- タイムアウト値は WASAPI が実際に確保したバッファ長の 1/2 から算出する。要求値(`EngineConfig::bufferMs`)ではない点が重要で、Windows は要求より大きいバッファを返すことが多い(実測では 10 ms 要求に対し 22 ms が返った)。この違いを見落とすと補填が消費に追いつかず、無音時に毎秒 60 回近い underrun が出る。

## 4. 実測結果(2026-08-03)

測定機: Windows 11 Pro / Visual Studio 18 (MSVC 19.51) / RelWithDebInfo

- 取り込み元: 「スピーカー (USB2.0 Device)」を **ループバック**(システム既定の出力)
- 出力先: 「スピーカー (Razer USB Audio Enhancer)」
- 信号: `audiolens_tone` による 1 kHz / -60 dBFS

WASAPI が確保したバッファは両エンドポイントとも 1056 フレーム(22.0 ms)、共有モードのミックス形式は 48 kHz / 2ch / float32 であった。

### 20 秒間

| 項目 | 値 |
|---|---|
| 取り込み | 968,160 フレーム(47,929 fps) |
| 再生 | 968,736 フレーム |
| underrun | 1(起動時のみ) |
| overrun | 0 |
| 不連続 | 1(起動時のみ) |
| ドリフト補正 | 0 |
| 推定遅延 | 22.0 ms |

### 5 分間(連続稼働)

`scripts\soak_test.ps1 -Seconds 300` による測定。

| 項目 | 値 |
|---|---|
| 取り込み | 14,407,200 フレーム(47,993 fps) |
| 再生 | 14,407,296 フレーム |
| underrun | 1(起動時のみ) |
| overrun | 0 |
| 不連続 | 1(起動時のみ) |
| ドリフト補正 | 0 |
| 無音補填 | 0 |
| 推定遅延 | 32.0 ms |

300 秒間でドリフト補正が 1 回も発生しなかったことから、この 2 デバイス間のクロック差はデッドバンド(264 フレーム = 5.5 ms)を 300 秒かけても超えていない、すなわち **約 18 ppm 未満** と分かる。リング充填量も 10〜20 ms の範囲で振れるだけで、一方向へ寄っていく傾向は見られなかった。

ただし 18 ppm でも 1 時間では約 3,100 フレーム(65 ms)蓄積し、リング容量(2,112 フレーム)を超える。ドリフト補正が実際に働くのはその領域であり、**要件どおりの 1 時間連続稼働テストは未実施** である。

### 遅延の内訳と注意点

推定遅延 22.0 ms は「リング充填 10.0 ms + 出力バッファ残 12.0 ms」である。**エンドポイント自体の遅延は含まれていない**: `IAudioClient::GetStreamLatency` が両デバイスとも 0 を返したためである。したがって実際のエンドツーエンド遅延はこれより大きい。要件 F-08(50 ms 目標 / 100 ms 上限)の最終判定には、ループバック録音による実測が別途必要である。

なお、統計に出るリング充填量は制御スレッドが任意のタイミングで読むため、再生スレッドが読み出した直後の谷を拾う。判断時点の実際の充填量は「表示値 + 出力バッファ残」に近く、目標値どおりに動作している。

## 5. オフラインテスト

`audiolens_tests` はハードウェアなしで実行でき、データ経路の正しさを検証する(29 テスト)。

- リングバッファ: 順序保持、ラップアラウンド(容量 16 に 10 フレームずつ 50 回)、満杯時の部分書き込み、空時の部分読み出し、`discard` / `writeSilence` の境界
- 形式変換: `WAVEFORMATEXTENSIBLE` の解釈、int16/int24/int32 の往復、クリップ、モノラル↔ステレオ、サラウンドからの 2ch 取り出し、パディング付きフレームストライド

実行:

```powershell
.\scripts\build.ps1
.\build\release\bin\audiolens_tests.exe
```

## 6. 既知の制限(M2 以降で対応)

| 項目 | 内容 |
|---|---|
| 1 時間耐久が未実施 | 実測は 5 分まで。M1 の出口条件を満たすには `scripts\soak_test.ps1 -Seconds 3600` の実行が必要 |
| リサンプラー未実装 | 取り込み元と出力先のサンプルレートが違うと起動を拒否する。サウンド設定で既定フォーマットを揃える必要がある |
| デバイス変更に未対応 | 抜き差しや既定デバイス変更を検知せず、`AUDCLNT_E_DEVICE_INVALIDATED` で停止する(要件 N-03) |
| エンドポイント遅延が測れない | `GetStreamLatency` が 0 を返すため、遅延の絶対値は外部測定が必要 |
| 内部は常に 2ch | サラウンド出力は先頭 2ch のみ。v1 のスコープどおり |
| ドリフト補正が素朴 | フレーム削除・複製方式。アダプティブリサンプラーへ置き換え予定 |

## 7. 使い方

```powershell
# ビルド
.\scripts\build.ps1                      # RelWithDebInfo
.\scripts\build.ps1 -Preset debug

# デバイス一覧
.\build\release\bin\audiolens_passthrough.exe --list

# パススルー(取り込み元は「再生デバイス」を指定。ループバックで取り込む)
.\build\release\bin\audiolens_passthrough.exe --capture "CABLE Input" --render "ヘッドホン"

# 信号発生
.\build\release\bin\audiolens_tone.exe --device 3 --freq 1000 --level -20 --duration 10

# 連続稼働テスト
.\scripts\soak_test.ps1 -Seconds 3600 -Capture 3 -Render 4
```
