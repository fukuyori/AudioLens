# M3.5: 堅牢化(N-03)実装メモ

- 版数: 0.1
- 作成日: 2026-08-03
- 対象: `src/dsp/resampler.*`、`src/engine/audio_engine.*`、`src/engine/device_watcher.*`、`src/app/audio_controller.*`

要件 N-03「デバイスの抜き差し・既定デバイス変更・サンプルレート変更に追従し、無音停止しない」は、必須要件で唯一の未達だった。M1〜M3 の実装では、

- 取り込み元と出力先のサンプルレートが違うと **起動を拒否** していた
- デバイスが変わると `AUDCLNT_E_DEVICE_INVALIDATED` で **停止したままになっていた**

---

## 1. リサンプラー

### 1.1 なぜ 1 つの部品が 2 つの問題を解くのか

サンプルレート変換とクロックドリフト補正は、どちらも「入力 1 フレームあたり何フレーム出力するか」を制御する問題である。前者は比率を固定値(例 44100/48000)に、後者はその比率を ppm 単位で微調整することで解ける。したがって可変比率のリサンプラーが 1 つあれば両方が片付く。

これは M1 のドリフト補正(充填量がデッドバンドを外れたらフレームを 1 つ削除・複製する)の置き換えでもある。旧方式は補正のたびに信号へ不連続を入れており、`docs/m1-engine-notes.md` §6 に既知の制限として挙げていた。

### 1.2 方式

窓関数付き sinc のポリフェーズ。32 タップ、512 位相、隣接位相間を線形補間。

- **各位相の係数を DC 利得 1.0 に正規化する。** これを怠ると、小数位置が進むにつれて出力レベルが揺れ、定常音でワブルとして聞こえる。
- ダウンサンプリング時はカットオフを **出力側** のナイキストに合わせる。入力側に合わせると折り返しが素通りする。
- 比率の微調整は ±2% に制限。係数は基準比率で設計されているため、大きく動かすと阻止域特性が崩れる。

### 1.3 検証(テスト 11 件)

| 検証項目 | 結果 |
|---|---|
| 48k↔44.1k の相互変換 | 周波数・振幅・出力長がいずれも正しい |
| DC 利得 | ちょうど 1.0 |
| 折り返し防止 | 48k→24k で 16 kHz(未対策なら 8 kHz へ折り返す)が -40 dB 以下 |
| 比率微調整 | 出力長が比例して変化 |
| チャンネル独立性 | 片チャンネルのみの信号で他方への漏れなし |
| 長時間動作 | 5 秒連続でバッファ前詰めが多数回発生しても位相ずれなし |

最後の項目は実装中に見つけたバグの回帰テストである。内部 FIFO を前詰めする際、絶対位置を保持する変数を同じ量ずらしていなかった。放置すれば最初の前詰めから音が壊れる。

なお当初のアンチエイリアシング試験は 48k→44.1k で 23 kHz を使っていたが、これは誤りだった。この条件ではカットオフが約 20.3 kHz で、23 kHz は阻止域ではなく遷移帯域に入る。またそもそも 48k→44.1k で折り返す成分は 20 kHz 以上にしか出ず、可聴域の試験にならない。レート半減の条件に変更した。

## 2. ドリフト制御ループ

再生スレッドが毎コールバックでリング充填量を見て、リサンプラーの比率を微調整する。

```
平滑化充填量 += 0.005 * (実測充填量 - 平滑化充填量)
充填誤差      = (平滑化充填量 - 目標) / 目標
比率トリム    = clamp(1 - 0.005 * 充填誤差, ±2000 ppm)
```

リングが溜まっているということは取り込みが再生を追い越しているので、出力 1 フレームあたりの入力消費を増やす = 比率を下げる、という向きになる。

### 2.1 ゲインを下げた経緯

最初は平滑化係数 0.02 / ゲイン 0.05 / 上限 ±5000 ppm で実装したが、実機で **発振した**。

```
[ 31s] クロック差 +265 ppm
[ 36s] クロック差 -501 ppm
最終    -1570 ppm
```

実測のクロック差は 18 ppm 未満(M1 で 5 分間ドリフト補正が 1 回も発生しなかったことから)なので、2 桁違う値を指している。比例ゲインが高すぎて、補正が充填量を目標より行き過ぎさせ、逆向きに補正する振動になっていた。

平滑化 0.005 / ゲイン 0.005 / 上限 ±2000 ppm に変更したところ、単調に収束するようになった。

```
[  5s] +252 ppm
[ 10s]  +45 ppm
[ 15s]   -2 ppm
[ 20s]   -0 ppm
```

比例制御なので、整定後は実ドリフトに比例した定常偏差が残る。20 ppm のドリフトなら充填誤差 0.4% で釣り合う計算で、実用上は無視できる。整定後の**比率トリムそのものが、実測されたクロック差である**。

## 3. デバイス変更の監視と復旧

### 3.1 なぜ監視が要るのか

WASAPI は動作中のクライアントにデバイス変更を直接伝えない。次の呼び出しが `AUDCLNT_E_DEVICE_INVALIDATED` で失敗するだけで、「何かが壊れた」ことは分かっても「いま何が使えるのか」は分からない。`IMMNotificationClient`(`src/engine/device_watcher.*`)がその穴を埋める。

- 通知は MMDevice のスレッドで来るため、Qt のキュー接続で GUI スレッドへ渡してからエンジンに触る。
- 既定デバイス変更は `eConsole` ロールのみ拾う。3 ロールすべてを拾うと 1 回の操作で 3 回発火する。
- ヘッドホンの抜き差しは `OnDeviceRemoved` ではなく `OnDeviceStateChanged` で来るため、そちらも扱う。

### 3.2 復旧の方針

エンジンが自力で停止し、かつ利用者がオンにしていた場合、`AudioController` が再接続を試みる。

1. 約 600 ms 待つ(Windows がデバイス変更後に落ち着くまで、即座の再試行は 2 度目の失敗を生むだけ)
2. デバイスを選び直す ― 利用者が選んだデバイスが戻っていればそれ、無ければ既定デバイス、それも駄目なら残ったもの
3. 起動を試みる。失敗なら 1 に戻る
4. 10 回失敗したら諦めて利用者に伝える

**復旧中は電源スイッチをオンのまま保つ。** 利用者はオンを望んでおり、勝手に戻ってくるのだから、ここでオフに見せるのは状態の誤表示であり、かつ復旧自体を打ち切ってしまう。

## 4. 実測結果(2026-08-03)

- サンプルレートが異なるデバイス間でも起動するようになった(状態表示に「48000→44100 Hz 変換」と出る)
- ドリフト制御ループは 15 秒で ±2 ppm 以内に整定
- GUI で 50 秒連続動作、underrun / overrun ともに 0、遅延 23.9 ms(うち処理 2.0 ms)
- リサンプラー導入前後で underrun は 1(起動時)→ 0 に改善

## 4.1 N-04: 既定デバイスを預かって必ず返す(2026-08-04 追加)

### 4.1.1 なぜ必要か

VB-Cable を既定の出力にして初めて、AudioLens は全アプリの音を受け取れる。この構成には嫌な性質がある。**AudioLens が動いていない瞬間、PC のあらゆる音が誰も聞いていないケーブルに流れ込む。**利用者に届くのは無音と、理由の手がかりゼロという状態である。

実測でも確認した。`--takeover` 付きで動かした passthrough を `TerminateProcess` で殺すと、

```
実行前     : スピーカー (Razer USB Audio Enhancer)  [既定]
実行中     : CABLE Input (VB-Audio Virtual Cable)   [既定]
強制終了後 : CABLE Input (VB-Audio Virtual Cable)   [既定]   ← 取り残される
```

### 4.1.2 既定デバイスの変更手段

**Windows には公開 API がない。**サウンド設定の画面は未公開の COM インターフェース `IPolicyConfig`(`CLSID_CPolicyConfigClient`)を叩いており、デバイスを切り替える各種ツールもすべて同じものを使っている。Vista 以来安定しており Windows 11 でも動くが、契約ではない。

そのため `src/engine/default_device.*` は**成功を前提にしない**。失敗は例外ではなく戻り値で返し、呼び出し側は「サウンド設定から手動で切り替えてください」に落ちる。利便性が下がるだけでアプリは動き続ける。

vtable は位置で対応するので、使わないメソッドもすべて宣言してある。1 つでも欠けたり型がずれたりすると、黙って別の関数を呼ぶことになる。

### 4.1.3 3 つの終わり方に 3 つの仕掛け

実行が終わる形は 3 通りあり、それぞれ別の機構が要る。

| 終わり方 | 機構 | 確実性 |
|---|---|---|
| 正常な停止・終了 | `DefaultDeviceGuard::release()` | 確実 |
| クラッシュ | `SetUnhandledExceptionFilter` で最期に復元 | 最善努力 |
| 強制終了・電源断・ブルースクリーン | **次回起動時に復元** | 確実 |

3 番目だけが常に成立するので、設計はそこに寄りかかっている。**切り替える前に**退避先を `settings.json` に書き、**復元した後に**消す。起動時にこの値が空でなければ、前回が返さずに死んだということである。

前の 2 つは、無音になっている時間を短くするためだけに存在する。

### 4.1.4 実測(2026-08-04)

取り残された状態を人工的に作って起動した。

```
--- 取り残された状態 ---
既定の出力      : CABLE Input (VB-Audio Virtual Cable)  [既定]
settings の記録 : {0.0.0.00000000}.{ce454d19-...}      ← Razer

--- AudioLens を起動 ---
既定の出力      : スピーカー (Razer USB Audio Enhancer)  [既定]
settings の記録 : ''                                    ← クリア済み
```

### 4.1.5 設計上の細部

- **書き込みは切り替えの前。**この 2 行の間で死ぬと、settings が指すデバイスはまだ既定のままなので、次回起動時の復元は何もしない no-op になる。失敗するなら無害な方向へ倒れる。
- **記録は切り替え成功後。**失敗した切り替えで、システムが一度もいなかった場所を復元先にしてしまうことがない。
- **クラッシュフィルタはロックを取らない。**そのミューテックスを持っているスレッドが、いま死んだ当人かもしれない。同じデバイスを二度設定するのは無害だが、設定しそこねるのは無害ではない。
- **動作中にデバイスを変えたら預け直す。**取り込み元が変われば既定も一緒に動かないと、システムはもう聞いていないデバイスへ音を送り続ける。
- 変更するのは `eConsole` と `eMultimedia` だけで、`eCommunications` は触らない。AudioLens が動いていないとき、通話は行き先のないケーブルではなく実機のヘッドセットに出るべきである。

### 4.1.6 復旧手段

万一取り残されたときのために、CLI から既定デバイスを直接戻せるようにした。

```powershell
audiolens_passthrough --set-default "Razer"
```

## 5. 復旧動作の検証(2026-08-04)

### 5.1 デバイス変更を意のままに起こす

これまで復旧動作を観測できなかったのは、デバイス無効化を再現する手段がなかったからである。挙がっていた案はどれも利用者の手を借りるものだった ― 既定デバイスの切り替え、USB の抜き差し、デバイスマネージャーでの無効化(要管理者権限)。

N-04 で `IPolicyConfig` を扱えるようになったことで、4 つ目の道が開けた。**エンドポイントの共有モード形式を変えると、Windows はそのエンドポイント上の全ストリームを無効化する。**要件 N-03 が挙げる「サンプルレート変更」そのものであり、管理者権限も物理操作も要らない。

```powershell
audiolens_passthrough --invalidate "CABLE Input"
```

サンプルレートを一時的に変えて元に戻す。これで `AUDCLNT_E_DEVICE_INVALIDATED` が確実に発生する。

### 5.2 検出したバグ 1: 復旧処理に一度も到達しない

初回の検証で、12 秒間に **720 回の停止記録、再接続の成功 0 回、諦めた記録 0 回**が出た。

原因は `AudioEngine::stop()` が `fault_` を消していなかったことである。消していたのは `start()` だけだった。結果として `AudioController::poll()` は毎回こうなる。

1. `faultReason()` が非空 → 停止処理へ入る
2. `engine_.stop()` を呼ぶ ― しかし fault はそのまま
3. `recoveryAttempts_ = 0` にリセットして `return`
4. 50 ms 後、同じ fault をまた検出して 1 に戻る

**復旧処理のブロックには一度も到達しない。**試行回数も毎回 0 に戻るので上限にも達せず、諦めることすらできない。ホットループのまま無限に回り続ける。

`stop()` が fault を消すようにした。fault は「対処されるまで報告され、対処後は報告されない」ものであり、停止は対処に当たる。

### 5.3 検出したバグ 2: 再試行回数が無限に戻る

上を直しても、**復旧に成功した直後にまた落ちる**場合に問題が残る。成功した時点で `recoveryAttempts_ = 0` になるため、直後の故障がまた 0 からやり直しになり、上限 10 回に永遠に届かない。デバイスが接続を受け付けては切る状態(フラッピング)で、アプリは何の結論も出せなくなる。

エンジンが**約 5 秒間持ちこたえてから**でなければ試行回数を返さないようにした。それ以前の故障は「まだ同じ問題が続いている」とみなす。

### 5.4 実測結果

```
17:28:44.164  エンジン開始: 48000 Hz
17:28:54.138  停止: AUDCLNT_E_DEVICE_INVALIDATED  — 再接続を試みます
17:28:54.901  キャプチャ: 44100 Hz / 再生: 48000 Hz
17:28:54.910  再接続しました (1 回目)
17:28:56.208  停止: AUDCLNT_E_DEVICE_INVALIDATED  — 再接続を試みます
17:28:56.968  再接続しました (1 回目)
```

- **故障から復旧まで 772 ms。**設計上の待機 600 ms に起動時間を足した値と一致する
- **復旧後は取り込み 44100 Hz / 出力 48000 Hz** で動作した。§1 のリサンプラーがそのまま効いており、レート変換への追従も同時に実証された
- 停止 2 回・再接続成功 2 回・諦め 0 回

### 5.5 まだ試していない経路

サンプルレート変更で `AUDCLNT_E_DEVICE_INVALIDATED` の経路は通ったが、**デバイスそのものが消える**場合は別の分岐(`resolveUsableDevice` による代替デバイスの選択)を通る。これは USB オーディオ機器の抜き差しでしか再現できない。

# 追補: 仮想ケーブル経由での音切れ(2026-08-04)

実利用で音の途切れが報告された。GUI の状態表示は 90 秒で **129 → 213 回**、CPU は 11〜17% と空いている。負荷ではない。

## 6.1 実測

CLI で内訳を取った(取り込み CABLE Input / 出力 Razer、95 秒)。

```
[  5s] 遅延 35.4 ms (リング 23.4)  underrun 0  overrun  3  クロック差 -1429 ppm
[ 10s] 遅延 51.9 ms (リング 39.9)  underrun 0  overrun  3  クロック差 -1092 ppm
[ 26s] 遅延 12.9 ms (リング  0.9)  underrun 0  overrun  6  クロック差 -1502 ppm
[ 41s] 遅延 12.0 ms (リング  0.0)  underrun 0  overrun  6  クロック差 -1022 ppm
[ 66s] 遅延 43.6 ms (リング 31.6)  underrun 0  overrun 11  クロック差 -1647 ppm
```

**リング充填が 0.0 〜 39.9 ms の全域を振動し、クロック差は -1000〜-1650 ppm に張り付いていた。**

## 6.2 原因 1: リングに余裕がない

```cpp
ringFrames = max(msToFrames(40ms), capture_.bufferFrames() * 2);
targetFillFrames_ = ringFrames / 2;
```

VB-Cable の取り込み周期は 1056 フレーム(22 ms)。40 ms 分より 2 周期分のほうが大きいので、**リングはちょうど 2 周期、目標充填は 1 周期**になっていた。

つまり **22 ms のパケットが 1 つ届けば満杯、1 周期抜ければ空**。余裕が一切ない。エンドポイントはメトロノームのようには届けてくれず、仮想ケーブルは供給側アプリの都合で動くので、1 周期ぶんの揺れは日常的に起きる。その揺れが毎回あふれか枯渇になっていた。

**4 周期に変更した。**目標の上下にそれぞれ 1 周期の余裕ができる。

## 6.3 原因 2: ループが配送ムラを追従していた

§2 の設計はこう書いていた。

> The drift the loop has to cancel is tiny and essentially constant: measured at under 18 ppm between two USB endpoints.

前提そのものは正しかった ― **実測でも真のクロック差は 126〜230 ppm** である。崩れていたのは別の前提だった。**仮想ケーブルは水晶ではなく、再生しているアプリの都合で音を渡してくる。**そのため充填量は、何も異常がなくても目標の上下 25 ms ほどを彷徨う。

比例ゲイン 0.005 では、この配送ムラだけでトリム要求が **±2841 ppm** に達する。上限 ±2000 ppm を超えるので、ループは常時飽和していた。飽和したループは制御していない。

**ゲインを 0.001 に、平滑化の時定数を 4.4 秒から 14.7 秒に下げた。**同じ ±25 ms の揺れに対する要求は ±568 ppm になり、上限が問題ではなくなる。

| | 変更前 | 変更後 |
|---|---|---|
| 位相余裕 | 65.5° | 72.4° |
| 定常充填誤差 | 1.1 ms | 5.5 ms |
| ±25 ms の揺れに対するトリム | **±2841 ppm(飽和)** | **±568 ppm** |

定常誤差が 5 ms 増えるが、リングには片側 22 ms の余裕がある。**比が揺れることは音程が揺れることであり、そちらのほうが高くつく。**

### 6.3.1 積分項を足して、外した経緯

一度は積分項を追加した。定常偏差 23% を消すためで、その 23% は「クロック差 1155 ppm」という読みから来ていた。

**その 1155 ppm は測定ではなく、故障の産物だった。**根拠にしたフレーム数の差は、overrun が取り込みフレームを破棄し、無音補填が別のフレームを足している最中に取ったものである。リングを適正な大きさにしたあとの同じ計算は 126〜230 ppm を返す。この値なら定常偏差は 2.5% であり、積分項が解くべき問題は存在しなかった。

しかも積分項は実害があった。**その零点が 0.09 rad/s、ループの交差周波数が 0.10 rad/s** で、位相余裕を 65° から 25° 前後まで削り、リングのほぼ全域を使う振動を起こした。上限とゲインをさらに上げると振れ幅は ±6000 ppm に達した。

削除した。**この日、同じ誤り ― 制御を速くすれば追従が良くなるという直感 ― を 3 回犯している。**残りの 2 回は遅いレベリング段で、`docs/m2-dsp-notes.md` 追補 §B.1 にある。

## 6.4 修正後の実測(125 秒、実音声を流した状態)

```
overrun     : 12 → 0
underrun    :  0 → 0
トリム       : ±2000 ppm に飽和 → -458 〜 +326 ppm(飽和なし、-230 ppm 付近へ収束)
リング充填   : 0〜40 ms → 30〜72 ms(目標 44 ms の周り)
推定遅延    : 22 ms → 70 ms
```

リングの揺れ自体は残っている。これは仮想ケーブルの配送そのもので、こちら側では消せない。**変わったのはループがそれを増幅しなくなったこと**で、リサンプラーの比が滑らかになった。

## 6.5 遅延の増加について

22 ms → 70 ms。内訳は 2 つある。

- リングを 2 周期から 4 周期に広げた(目標充填が 1 周期から 2 周期へ)
- 比例ゲインを下げたぶん定常充填誤差が 1.1 ms から 5.5 ms に増えた

成功基準 3(リップシンク 100 ms 以下)には収まるが、余裕は削っている。

**縮める本命は `IAudioClient3` である。**現在は旧 API で共有モードの周期が 22 ms 固定になっており、リングはその 4 倍である。`InitializeSharedAudioStream` でデバイスの最小周期(多くは 3〜10 ms)を要求できれば、リングも遅延も比例して縮む。

## 6.6 教訓

制御ループの帯域は、抑えたい外乱の帯域より**十分下**になければならない。同じ誤りをこの日 2 回犯している ― 遅いレベリング段(`docs/m2-dsp-notes.md` 追補 §B.1)でも、番組の変動と同じ速さで動く制御が変動を**増やして**いた。どちらも「速く反応すれば良くなる」という直感が逆に働く場面だった。

## 6.7 `IAudioClient3` を試した結果(2026-08-04)

§6.5 で挙げた「遅延を縮める本命」を実装し、**効果がないことが分かった**ので記録する。

`IAudioClient::Initialize` は要求した長さを下限としてエンジンの周期へ丸め上げる。10 ms を要求して 22 ms を渡されるのは日常で、下流はすべてその周期から寸法を決めるため、これがパイプライン全体の遅延の下限になる。`IAudioClient3::InitializeSharedAudioStream` は周期そのものを選べる。

実測(取り込み CABLE Input / 再生 Razer):

```
キャプチャ: 要求 480 / 既定 480 / 最小 128 / 最大 480 / 基本 1 フレーム
            → AUDCLNT_E_INVALID_DEVICE_PERIOD
再生      : 低遅延パス成功 / 周期 480 フレーム (既定 10.0 ms / 最小 10.0 ms)
```

**取り込み側は既定値そのものを要求して拒否された。**範囲内、基本周期は 1 なのであらゆる値が正当な倍数、つまり要求に瑕疵はない。成功した再生側との唯一の違いは `AUDCLNT_STREAMFLAGS_LOOPBACK` である。**ループバックは低遅延パスに対応していない。**

再生側は通ったが、そのエンドポイントは**最小周期が既定と同じ**で、得るものがなかった。

AudioLens の取り込みは常にループバックなので、**この経路で遅延は縮まない**。実装は残す ― 失敗しても従来のパスへ戻るだけで害がなく、ログがエンドポイントの素性を語るためである。

### 遅延の下限は何で決まるか

したがって遅延を決めているのは WASAPI の周期ではなく、**仮想ケーブルの配送の不均一さ**である。§6.3 のとおり充填量は正常時でも目標の上下 25 ms を彷徨うので、リングはそれを飲み込める大きさでなければならない。周期を短くしてもこの揺れは縮まない。

縮めるならこの順になる。

1. **VB-Cable 側の設定** ― `C:\Program Files\VB\CABLE\VBCABLE_ControlPanel.exe` に内部バッファの設定がある。配送が均一になれば、リングを小さくできる
2. **配送のより均一な仮想デバイス**に替える
3. リングを 4 周期から 3 周期へ ― 遅延は 11 ms 縮むが、実測した揺れに対する余裕がほぼなくなる。§6.2 で直したばかりの問題に戻る
