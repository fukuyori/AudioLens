## 1. 方式選定

### 1.1 採用方式: 仮想オーディオデバイス方式

システムの既定出力を AudioLens の仮想出力デバイスに切り替え、アプリがそこから音声を取り込み、DSP 処理後に実出力デバイスへ再生する。

```
[各アプリの再生音]
      │  (Windows オーディオエンジンがミックス)
      ▼
[AudioLens 仮想出力デバイス]  ← システム既定デバイスに設定
      │  WASAPI ループバック/キャプチャ
      ▼
[AudioLens エンジン (ユーザーモード)]
      │  DSP チェーン処理
      ▼
[実出力デバイス (ヘッドホン/スピーカー)]  ← WASAPI 共有モード再生
```

### 1.2 比較検討した方式

| 方式 | 長所 | 短所 | 判定 |
|---|---|---|---|
| 仮想デバイス方式(採用) | ユーザーモードで DSP を開発でき、デバッグ容易。全システム音を確実に取得。将来のプロセス別処理とも併用可 | ドライバの同梱・署名が必要。既定デバイス切替の UX 配慮が要る | ✅ 採用 |
| APO 方式(Equalizer APO 系) | OS パイプライン内で低遅延。追加の再生パスが不要 | デバイスごとの登録が必要。開発・デバッグ難度が高い。OS アップデートの影響を受けやすい。A/B 比較やメーター等アプリ連携が複雑 | ❌ 見送り |
| プロセスループバック単独 | アプリ別取得が容易 | 元の再生音を消せず、補正音と二重再生になる | ❌ 単独では不成立(v2 で併用) |

### 1.3 仮想デバイスドライバの調達

| 選択肢 | 備考 |
|---|---|
| **Microsoft `simpleaudiosample` をベースに自作(採用)** | Windows-driver-samples の `audio/simpleaudiosample`。12,569 行と小さく、単一の仮想オーディオエンドポイントの最小実装。レンダーのみに絞って利用 |
| `sysvad` をベースに自作 | 同リポジトリの `audio/sysvad`。57,117 行あり、Bluetooth・USB ヘッドセット等の多数のエンドポイントを含む。削ぎ落とす手間に見合わない |
| 既存サードパーティドライバ(VB-Cable 等)の同梱 | 再配布ライセンス契約が必要。開発初期の検証用途には可 |

**ライセンスは MS-PL(Microsoft Public License)である。** 当初 MIT と記載していたが誤りだった。派生ソースを配布する場合はその部分を MS-PL 下に置き、上流の著作権表示を保持する必要がある。コンパイル済みバイナリの配布と、AudioLens 本体を別ライセンスにすることは妨げられない。詳細は `driver/README.md`。

署名は **アテステーション署名**(EV 証明書 + Partner Center)を目標とする。HLK テストが不要で、要件 N-06 の対応 OS 範囲(Windows 10 以降)と一致する。

ただし手持ちのコード署名証明書(`CN=Noriaki Fukuyori`、GoGetSSL 発行)は **OV であって EV ではない**(2026-08-04 確認)。アプリ本体とインストーラーの署名にはそのまま使えるが、Partner Center のハードウェア開発者アカウント登録には使えない。

**EV は登記済みの事業体にしか発行されない。**Azure Trusted Signing は代替にならないことも確認済み(Microsoft が Hardware Developer Program では EV を要求し続けており、かつ個人枠は米加在住者限定)。したがってドライバを同梱して配布するには法人格が要る。この判断が M4 の配布形態を左右するため、実装より先に方針を決める必要がある。選択肢は `driver/README.md` §5.0.2。

**開発フェーズの割り切り**: ドライバ完成前は、開発マシンに VB-Cable 等を手動インストールして「仮想デバイス相当」とみなし、エンジン開発を先行させる。エンジンから見えるのは単なるキャプチャ元デバイスであり、ドライバ差し替えの影響を受けない。

### 2.2 モジュール責務

| モジュール | 責務 | 主要技術 |
|---|---|---|
| `AudioEngine` | キャプチャ→DSP→レンダーのリアルタイムループ。フォーマット交渉、リサンプル、デバイス障害からの復旧 | WASAPI(イベント駆動・共有モード)、専用高優先度スレッド(MMCSS "Pro Audio") |
| `DspChain` | フィルタ群の直列処理。パラメータのスレッドセーフな更新(ロックフリー) | 自作 DSP(biquad、コンプレッサー、リミッター) |
| `AppCore` | プリセット/設定の読み書き、3 スライダー→DSP パラメータへのマッピング、既定デバイス切替、デバイス監視 | `IMMDeviceEnumerator`、`IPolicyConfig`(既定デバイス切替)、JSON |
| `UI 層` | メイン画面、トレイ常駐、A/B 比較、レベルメーター | 後述 2.4 |
| `Driver`(別プロジェクト) | 仮想レンダーエンドポイント提供 | WDM/PortCls(sysvad ベース) |

### 2.3 スレッドモデル

| スレッド | 役割 | 制約 |
|---|---|---|
| オーディオスレッド | capture→DSP→render の 1 ループ。イベント駆動(10 ms 周期目安) | メモリ確保・ロック・COM 呼び出し禁止。パラメータはロックフリーで受領(atomic なパラメータブロックのダブルバッファ) |
| UI スレッド | 画面・トレイ | — |
| 制御スレッド | デバイス監視、復旧、設定保存 | デバイス変更通知(`IMMNotificationClient`)はここへディスパッチ |

### 2.4 UI フレームワーク

**決定: Qt 6 Widgets を採用**(M3 で確定)。

| 候補 | 評価 |
|---|---|
| **Qt 6 Widgets(採用)** | レイアウト・トレイ常駐・JSON・標準ダイアログが揃い、UI の工数が最小。msvc2022_64 キットが既存の MSVC ビルドとそのまま噛み合う。多言語化の道具も同梱 |
| Win32 + Direct2D 自前描画 | 依存ゼロ・軽量・常駐向き。UI 部品を自作する工数がかかる |
| WinUI 3 | モダンな見た目。ランタイム配布とトレイ常駐の相性に注意 |

Qt に依存するのは `src/app/` だけで、エンジン・DSP・テストは Qt なしでビルドできる。詳細は `docs/m3-gui-notes.md`。

## 3. DSP 設計

### 3.1 処理チェーン

```
入力 (float32, 2ch, 48kHz 内部固定)
  → [1] 入力ゲイン
  → [2] ハイパスフィルタ (低音の濁り抑制)         … biquad HPF 12dB/oct
  → [3] 低域シェルフ (低音量感の調整)             … low-shelf
  → [4] スピーチ帯域強調 (声の明瞭さ)             … peaking EQ 複数バンド (中心 1〜4 kHz)
  → [5] 高域シェルフ (高域の補整・抑制)           … high-shelf
  → [6] ワイドバンドコンプレッサー (音量差の平準化) … ラウドネス連動、soft-knee
  → [7] メイクアップゲイン + 出力音量
  → [8] ルックアヘッドリミッター (安全装置, -1 dBFS)
  → 出力
```

- 内部処理は float32 / 48 kHz / 2ch に統一し、入出力で必要に応じてリサンプル(高品質ポリフェーズ)。
- パラメータ変更はブロック境界でスムージング(クリックノイズ防止、20〜50 ms ランプ)。
- A/B 比較はチェーン全体のバイパスをクロスフェード(50 ms)で切り替える。

M2 実装時の変更点:

- [6] のコンプレッサーは **RMS 検出**(10 ms 窓)とした。ピーク検出では波形に利得が追従してしまい、「音量差を整える」という目的に合わない。波形の振れを抑えるのは [8] のリミッターの役割である。
- スムージングは 32 フレーム(0.67 ms)のサブブロック単位で行い、係数の再設計は制御値が実際に動いたときだけ実施する。バイパスは現状クロスフェードではなく即時切り替えで、リミッターだけは常に通して遅延と安全性を保つ。
- オーディオスレッドでは denormal 演算を無効化する必要がある(`src/common/denormals.h`)。

### 3.2 スライダー→パラメータのマッピング

ユーザーに見える 3 項目(各 0〜100)は、プリセットが定める基準値に対する強度スケールとして働く。

| スライダー | 主に動かすパラメータ |
|---|---|
| 低音 | [2] HPF カットオフ(0=オフ 〜 100=150 Hz 程度)、[3] 低域シェルフゲイン(±) |
| 声の明瞭さ | [4] スピーチ帯域の各バンドゲイン(0〜+8 dB 程度)、バンド幅 |
| 音量差 | [6] コンプレッサーのレシオ(1:1〜8:1)・スレッショルド・メイクアップの連動カーブ |

マッピングテーブル自体をプリセット定義(JSON)に持たせ、コード変更なしにチューニング可能とする。

### 3.3 遅延バジェット(目標 50 ms / 上限 100 ms)

| 区間 | 見積り |
|---|---|
| OS ミキサー → 仮想デバイス | 約 10 ms |
| キャプチャバッファ | 10 ms |
| DSP(リミッターのルックアヘッド含む) | 1〜5 ms |
| レンダーバッファ | 10 ms |
| 実デバイス出力 | 約 10 ms |
| **合計** | **約 40〜45 ms** |

M1 の実測では、要求 10 ms に対し WASAPI が確保したバッファは両エンドポイントとも 22 ms であった。バッファ長は要求値ではなく実際に確保された値を前提に設計すること。またエンドポイント自身の遅延は `IAudioClient::GetStreamLatency` が 0 を返す機種があり、遅延の絶対値はループバック録音による外部測定が必要となる。詳細は `docs/m1-engine-notes.md`。

## 4. データ設計

### 4.1 保存場所

`%APPDATA%\AudioLens\`

```
settings.json      … アプリ設定(選択デバイス、自動起動、最後のプリセット等)
presets\
  builtin\         … 組み込みプリセット(読み取り専用、インストール先からコピーしない)
  user\*.json      … ユーザープリセット
```

### 4.2 プリセットスキーマ(抜粋)

```json
{
  "schemaVersion": 1,
  "name": "映画",
  "id": "builtin.movie",
  "device": null,
  "sliders": { "bass": 40, "clarity": 55, "leveling": 75 },
  "mapping": {
    "hpf":     { "freqAt100": 120.0 },
    "speech":  { "bands": [ { "freq": 2000, "maxGainDb": 6.0, "q": 1.0 } ] },
    "comp":    { "maxRatio": 6.0, "thresholdDb": -28.0, "attackMs": 10, "releaseMs": 250 }
  }
}
```

`device` に出力デバイス ID を設定したユーザープリセットは、そのデバイスがアクティブになった際の自動適用候補となる(F-13)。

## 5. 主要シナリオの動作

| シナリオ | 動作 |
|---|---|
| 起動 | 仮想デバイスの存在確認 → 既定デバイスを仮想デバイスへ切替(元の既定を記憶)→ エンジン開始 |
| 終了・クラッシュ | 通常終了時は既定デバイスを復元。異常終了に備え、起動時に「前回の既定デバイス」を settings.json から復元可能にする(N-04) |
| 実デバイスの抜去 | 制御スレッドが検知 → エンジン停止 → 代替デバイス(次の既定)で再開。復旧不能ならバイパス(既定を実デバイスへ戻す) |
| サンプルレート変更 | エンジン再初期化(1 秒以内の復帰目標) |
| A/B 比較 | DSP バイパスフラグをクロスフェード切替。経路・遅延は変えない(公平な比較のため) |

## 6. リポジトリ構成(案)

```
AudioLens/
├─ docs/                  … 本ドキュメント群
├─ src/
│  ├─ app/                … エントリポイント、常駐、UI
│  ├─ core/               … AppCore(設定・プリセット・デバイス管理)
│  ├─ engine/             … AudioEngine(WASAPI キャプチャ/レンダー)
│  ├─ dsp/                … DspChain とフィルタ実装(OS 非依存・単体テスト対象)
│  └─ common/             … ログ、ユーティリティ
├─ driver/                … 仮想デバイスドライバ(sysvad ベース、別ソリューション)
├─ tests/                 … dsp/core の単体テスト(オフラインで WAV 処理検証)
├─ installer/             … インストーラースクリプト
└─ CMakeLists.txt
```

M1 時点の実際の構成では、`src/app/` `src/core/` `src/dsp/` `driver/` `installer/` はまだ存在せず、代わりに検証用 CLI として `src/tools/passthrough/`(取り込み→再生)と `src/tools/tone/`(信号発生)、および連続稼働テスト用の `scripts/` がある。

- ビルド: CMake + MSVC(C++20)。ドライバのみ WDK/Visual Studio ソリューションで別管理。
- `dsp/` は Windows API 非依存とし、WAV 入出力によるオフラインテスト(ラウドネス計測含む)で品質検証する。

## 7. 開発ロードマップ

| フェーズ | 内容 | 出口条件 |
|---|---|---|
| M1: エンジン検証 ✅ | 既存仮想デバイス(VB-Cable 等)を使い、キャプチャ→パススルー→再生を実装 | 遅延実測 50 ms 以下、1 時間グリッチなし。実装・実測は `docs/m1-engine-notes.md` |
| M2: DSP コア ✅ | DspChain 実装+オフラインテスト。3 スライダーのマッピング | WAV 検証でプリセット効果を LUFS/スペクトルで確認。実装・実測は `docs/m2-dsp-notes.md` |
| M3: アプリ統合 ✅ | UI(最小)、プリセット、A/B 比較、トレイ常駐、デバイス監視 | 要件 F-01〜F-35 の必須項目充足。実装・実測は `docs/m3-gui-notes.md`(F-13/F-14/F-23 と英語対応は積み残し) |
| M4: ドライバ ❌ | simpleaudiosample ベース仮想デバイス | **中止(2026-08-04)。**自作カーネルドライバは使わない方針とした。ビルド成功までの記録として `driver/` を残す。`driver/README.md` |
| M5: 仕上げ | 安定化、8 時間耐久、成功基準の計測 | requirements.md §5 達成 |

**M4 中止の主たる理由は安全性である。**カーネルモードのバグはブルースクリーンや起動不能を招く。仮想オーディオデバイスは音の入口にすぎず、そこに OS 全体を巻き込む故障モードを持ち込む価値はない。広く配布され Microsoft の署名を受けた既存ドライバのほうが、実地の検証量で圧倒的に勝る。署名が取得できない件(`driver/README.md` §5)は従たる理由にすぎない。

これにより取り込み元は VB-Cable 等の既存仮想デバイスに固定される。M1 で「開発フェーズの割り切り」としていた構成が、そのまま最終形になる。エンジンから見えるのは単なるキャプチャ元デバイスなので、実装への影響はない。詳細は `docs/requirements.md` §4.1。

## 8. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| ~~ドライバ署名(EV 証明書・Partner Center)の取得に時間・費用~~ | ~~M4 遅延~~ | **顕在化した。**EV は登記済み事業体にしか出ず、代替経路も塞がっていた。個人利用のみとする決定で M4 を凍結し、既存仮想デバイスを使う形に収束(2026-08-04) |
| 排他モード・DRM 再生アプリの音が取れない | 一部アプリ非対応 | 制限事項として明示。既知アプリのリストを FAQ 化 |
| 既定デバイス切替 API(IPolicyConfig)が非公開 API | OS 更新で破損の可能性 | 失敗時はユーザーに手動切替を案内するフォールバック UI を用意 |
| 遅延がリップシンク許容を超える環境がある | 動画視聴で違和感 | バッファサイズ設定(自動/低遅延/安定重視)を用意 |
