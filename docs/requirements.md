# AudioLens 要件定義書

- 版数: 0.1(ドラフト)
- 作成日: 2026-08-03
- 対象プラットフォーム: Windows 10 (2004 / Build 19041) 以降、Windows 11

---

## 1. プロジェクト概要

### 1.1 目的

AudioLens は、PC で再生されるあらゆる音声を、用途に合わせて「聞き取りやすく」調整するプリセット型オーディオ補助アプリである。専門的な周波数知識を持たない利用者が、プリセットの選択と少数の分かりやすいツマミ操作だけで、以下の効果を得られることを目的とする。

- 低音の濁り(こもり)の抑制
- 人の声に必要な周波数帯の強調による明瞭度向上
- 大きすぎる音・小さすぎる音の音量差の自動平準化

### 1.2 ターゲットユーザー

| ユーザー像 | 代表的な利用シーン |
|---|---|
| オンライン会議・通話の利用者 | 相手の声が聞き取りにくい会議、録音の聞き直し |
| 学習者 | 講義動画・ポッドキャストの長時間視聴 |
| 映画・動画視聴者 | セリフが小さく効果音が大きい映画の音量差解消 |
| 深夜利用者 | 家族に配慮した小音量でもセリフが聞こえる状態 |
| 聴取に不安のある利用者 | 高域の聞き取り低下などを補う日常的な補助 |

専門用語(周波数、dB、コンプレッサー等)を知らないユーザーを主対象とする。UI 上ではこれらの用語を直接露出しない。

### 1.3 スコープ外(本バージョンでは扱わない)

- マイク入力(自分の声)の加工
- 録音・ファイル書き出し機能
- macOS / Linux 対応
- 医療機器としての聴覚補助(補聴器の代替を謳わない)

### 2.2 プリセット

| ID | 要件 | 優先度 |
|---|---|---|
| F-10 | 組み込みプリセットを提供する: 「標準(素通し)」「会話」「講義」「映画」「深夜」「ゲーム」、および音楽向けの「ロック」「ジャズ」「クラシック」「アンビエント」の 10 種 | 必須 |
| F-11 | プリセットはワンクリックで切り替えられ、即時に反映される | 必須 |
| F-12 | ユーザーはプリセットを元に調整した状態を独自プリセットとして名前を付けて保存できる | 必須 |
| F-13 | 独自プリセットは出力デバイス(ヘッドホン/スピーカー等)と関連付けて保存でき、デバイス切替時に自動適用できる **✅ 実装済み(2026-08-04)** | 高 |
| F-14 | プリセットのエクスポート/インポート(ファイル共有) | 低 |

組み込みプリセットの意図。 **`id` は `--preset` に渡す値** (F-36)で、画面に出ている表示名でも指定できる。並びは画面と `--list-presets` の並びに一致する。

| id | 表示名 | 意図 | 処理の傾向 |
|---|---|---|---|
| `standard` | 標準 | 何もしない | 全項目・0。素通し・遅延 0 ms |
| `conversation` | 会話 | 通話・会議の声を聞き取りやすく | 声帯域強調・強め、低域カット中、音量平準化・強め |
| `lecture` | 講義 | 長時間聴取で疲れにくく | 声帯域強調・中、音量平準化・中、高域刺激を抑制 |
| `movie` | 映画 | セリフと効果音の音量差を縮める | 音量平準化・強め、声帯域強調・中、低域は残す |
| `night` | 深夜 | 小音量でも聞こえるダイナミクス圧縮 | 音量平準化・最強、低域カット強め(近隣配慮) |
| `game` | ゲーム | 足音など小さな音と、その方向を分かりやすく | 低域カット・最強、中高域強調・強め、ステレオ拡張、リミッター先読み短縮 |
| `rock` | ロック | 歪んだギターの壁からボーカルを引き出す | ハイパス 60 Hz(キックの基音より下だけ)、250 Hz の濁りを -2.5 dB、1.6k/3.4 kHz を強調、ミッドのみ持ち上げサイドは維持 |
| `jazz` | ジャズ | 少人数編成の各楽器を分離させ、耳に痛い上だけ丸める | ハイパス 50 Hz(ウッドベースを残す)、2.5 kHz を控えめに、10 kHz を -1.5 dB(シンバル)、ミッド/サイド処理なし |
| `classical` | クラシック | ダイナミクスとホールの響きを保ち、極力触らない | ハイパス 40 Hz、3 kHz を +1.5 dB、ミッド/サイド処理なし(空間情報がサイドにある) |
| `ambient` | アンビエント | 上の細部だけわずかに上げ、広がりと寄せ引きに触れない | ハイパス 45 Hz、4 kHz を +1.5 dB、12 kHz を +1 dB、ミッド/サイド処理なし |

**音楽向けの 4 つは音量差を整えない。** 録音のダイナミクスは編曲そのものであり、レコードは意図をもって一度圧縮されている。二度目をかけることは一度目の改善にならない。実測でも「映画」が LRA 17.99 → 13.13 LU と縮めるのに対し、音楽プリセットは 17.99 → 17.99 LU と変えない。これは不具合ではなく、この 4 つの合格条件である(§5 の基準 1 は音声向けプリセットに対するもの)。

#### 2.4.1 コマンドライン制御(F-36)

`AudioLens.exe --preset movie --volume 70` のように起動すると、 **すでに常駐しているアプリに指令が届き、即座に反映される。** 常駐していなければ、その設定で起動する。オプションを付けない起動はウィンドウを前面に出す。

**なぜ「起動時オプション」ではなくこの形なのか。** AudioLens は常駐アプリである。起動時にしか効かない指定は、一日に一度しか使えない。ホットキーやバッチから曲やアプリに合わせてプリセットを切り替えたいという用途は、動いているものを変えられなければ成立しない。

| 分類 | オプション |
|---|---|
| 音 | `--preset <id>` `--volume <0-100>` `--volume-step <±n>` `--balance <-50..50>` `--bass` `--clarity` `--leveling` (各 0-100) |
| 処理 | `--on` `--off` `--toggle` `--bypass on\|off` |
| 経路 | `--output <名前>` `--input <名前>` |
| 報告 | `--status` `--list-presets` `--list-outputs` |
| ウィンドウ・プロセス | `--show` `--hide` `--quit` `--minimized` `--verbose` `--version` `--help` |

`--preset` に渡せる値は §2.2 の表にある 10 個の `id`。 **画面に出ている表示名でも指定できる** — 「映画」でも `movie` でも通る。訳前の英語表示名 `Film` も受け付ける。実行中のものは `--list-presets` が id と表示名を並べて出す(独自プリセットを含む)。

`--output` と `--input` はデバイスを **名前で** 指定する。デバイス ID は安定した不透明な文字列で、手で打てるものではない。名前は一部で足り、`--output USB2.0` のように書ける。 **複数に当たったときは推測せず拒否する** — 出力先を取り違えても画面には何も起きず、「音が出ない」としてしか気づけないためである。候補を並べて終了コード 1 で終わる。完全一致は部分一致より先に判定する。そうしないと「スピーカー」が「スピーカー (USB2.0 Device)」の一部でもあるため、正確に名指ししても曖昧と言われて選べない。

指定できる名前は `--list-outputs` が出す。1 つの一覧が `--output` と `--input` の両方に使えるのは、取り込み側がループバックで再生デバイスを叩いているためである。現在の出力先・取り込み元・システム既定には印が付く。

終了コード:

| コード | 意味 |
|---|---|
| `0` | 実行した |
| `1` | 常駐していない、または実行できなかった(エンジンが起動できなかった等) |
| `2` | コマンドラインが不正(未知のオプション、範囲外の値、値の欠落) |

**`--quit` だけは、常駐していなくても `0` を返す。** 求められた状態(動いていない)は既に成り立っており、それを失敗と呼ぶ理由がない。`AudioLens.exe --quit` に続けてファイルを差し替えるような使い方で、動いていなかったという理由で止まってしまうのは筋が通らない。

`1` と `2` を分けるのは、バッチから見て打つべき手が違うためである。`2` はスクリプト自体の誤りで、直すまで何度実行しても同じになる。`1` は状況によるもので、再試行に意味がありうる。

設計上の判断:

- **フラグは書いた順ではなく、決められた順に適用する。** プリセットを選ぶと 3 スライダーはそのプリセットの値に戻る(F-11 の「即時に反映」がそう定義されている)。左から順に処理すると `--bass 20 --preset movie` は 20 を捨てる。プリセットを先に当てることで、同じ命令をどちらの順で書いても同じ意味になる。
- **経路の変更は、プリセットよりさらに先に当てる。** 出力先を変えると、そのデバイスに記憶された内容 — プリセット・3 スライダー・音量・バランス(F-13) — が適用される。同じコマンドラインに載った `--volume` はその後でなければ、プロファイルに上書きされて消える。同じ規則を一段外側へ広げたものである。
- **指定しなかった項目は動かさない。** コマンドラインは状態の全体像ではなく、いま動いているものへの差分である。`--preset movie` が音量まで既定値に戻すようであってはならない。
- **範囲外の値は丸めず拒否する。** `--volume 700` は打ち間違いであり、黙って 100 にすると打ち間違いが隠れる。未知のオプションも同様に拒否する — ほぼ必ず既知のオプションの綴り間違いであり、それだけを落として他を実行すると、意図した指定だけが消える。
- **`--volume-step` を `--volume` と分ける。** バランスは -50〜+50 なので、先頭のマイナスはすでに「左側の絶対位置」を意味している。同じ記法が一方では相対、他方では絶対になると、書いたホットキーが当たるかどうかは運になる。
- **ウィジェットを経由して適用する。** 画面の再描画・設定ファイルへの保存・デバイス別プロファイル(F-13)の更新は、すべてスライダーやリストのハンドラが行っている。モデルを直接叩くと、画面と実際の処理が食い違い、変更が保存されなくなる。
- **`--bypass` は保存しない。** 画面の A/B ボタンが押しっぱなし式なのと同じ理由で、バイパスは聴きながら行う操作であって、うっかり入れたまま残して「効かない」と報告される状態ではない。
- **問い合わせのためにアプリを起動しない。** 常駐していないときに `--status` を打つと、答えるためにアプリを起動することになる。それは質問自身への答えになってしまううえ、まさに尋ねた対象を裏で残す。「起動していません」と言って終了する(終了コード 1)。状態を変えるオプションは逆で、「音をこうしてほしい」という指定なので、その設定で起動するのが素直な読み方になる。
- **「誰もいない」と「届かなかった」を区別する。** 当初は失敗をすべて「起動していない」に潰していた。パイプ交換が途中で失敗すると 2 個目を起動することになり、この経路が閉じるはずの N-04 の危険をそのまま作る。`ServerNotFoundError` だけを「いない」とし、それ以外は理由を表示して **起動せずに** 終了する。
- **プリセット名は画面に出ている形で照合する。** 画面は「映画」と表示し、ソース文字列は `Film` である。訳語で照合しないと、目の前にあるものを打って「そんなプリセットはない」と言われる。訳前の形も受け付ける — 別の言語の PC で走らせるスクリプトのため。

**チャネルの獲得そのものを、単一インスタンスの決着に使う。** 当初はウィンドウ構築の最後に開いていた。プリセット・デバイス列挙・WASAPI 起動で、cold start では 1.9 秒かかる(warm start は 0.11 秒)。 **その間に来たコマンドラインは「起動していない」と判断され、状態を変えるものなら 2 個目を起動していた。**

実測で再現した。失敗するクライアントは接続に失敗した時点で即座に終了するので 1 回あたり約 75 ms、20 回連続で試しても約 1.5 秒にしかならず、 **全 20 回が 1.9 秒の窓の内側に収まって全滅した。**

**「先に聞いて、いなければ起動する」という順序では、この競合は原理的に解けない。** 他方の `CreateProcess` から `listen()` 到達までには必ず隙があり、そこで接続すると誰もいないように見えるからである。名前の獲得なら解ける — パイプは `FILE_FLAG_FIRST_PIPE_INSTANCE` で作られるので、 **勝てるのは 1 プロセスだけ** である。よって `main()` はウィンドウを作る前にチャネルを獲りにいき、獲れなければ「勝者がいる」ということなので、もう一度そちらへ渡しにいく。

ウィンドウより先に開いても安全である。接続はパイプに待ち行列として溜まり、ハンドラはイベントループが回るまで動かない — すなわちウィンドウが建ってからにしかならない。 **これは、そこまでの間に入れ子のイベントループが回らない限りでのみ成り立つ** (コンストラクタにモーダルダイアログを置いてはならない)。応答待ちを 15 秒と長く取ってあるのも同じ理由で、起動途中のアプリは待てば答える。待たずに諦めると 2 個目を起こす。

獲得に失敗し、かつ問い合わせても誰もいなかった場合は、そのまま起動する。チャネルが何らかの理由で開けないだけであり、無ければ F-36 以前と同じ、すなわち普通に使えるアプリである。それを理由に起動を拒むのは筋が悪い。

実測: 起動と同時にコマンドを撃つ試験を 5 回、いずれも 1 回目で成功(150〜159 ms)。修正前は同じ試験で 20 回連続失敗していた。

**副産物として単一インスタンスになった。** それまで 2 個目を起動すると、両方が既定出力デバイスを自分の取り込み先へ向け、あとから終了したほうが「もう置き換えられているデバイス」を復元していた(N-04 の前提が崩れる)。2 個目が指令を渡して終了することで、この経路が閉じた。

**経路は名前付きパイプで、ユーザーごとに分けてある** (`QLocalServer`、`UserAccessOption`)。同じ PC に 2 人が同時にサインインしていても、一方が他方の音量を変えることはない。

**出力先はコンソール。** ウィンドウアプリには標準出力がないため、`AttachConsole` で呼び出し元のコンソールを借りる。ただしシェルはウィンドウアプリの終了を待たないので、文字はプロンプトが戻ったあとに現れる。順に読みたい場合は `Start-Process -Wait -NoNewWindow` を使う。コンソールへは UTF-16 で直接書くため、コードページによらず日本語のプリセット名が化けない。

## 4. 制約・前提

### 4.1 適用範囲: 一般配布する / 自作ドライバは使わない(2026-08-06 改定)

**AudioLens は一般に配布する。ただし自作のカーネルモードドライバは使用しない。**

2026-08-04 には「個人利用のみ」としていた。 **その判断は 2 つの独立した理由からなり、片方だけが消えた。**

**(1) 自作カーネルドライバを使わない ― 安全性の判断。これは変わらない。** カーネルモードのコードは失敗の代償が大きい。ユーザーモードのバグはアプリが落ちるだけだが、カーネルモードのバグはブルースクリーン、起動不能、最悪の場合ファイルシステムの破損になる。仮想オーディオデバイスは AudioLens の中核ではなく音の入口にすぎず、そこに OS 全体を巻き込む故障モードを持ち込む価値はない。 **VB-Cable のように広く使われ、Microsoft の署名を受けて配布されているドライバは、実地で桁違いの検証を経ている。** 自作より安全である。

**(2) 一般配布しない ― 実現性の判断。これが消えた。** この理由は「ドライバを同梱するなら Partner Center 由来の Microsoft 署名が要り、その登録には EV 証明書が要り、EV は登記済みの事業体にしか出ない」というものだった。 **(1) の結論としてドライバを同梱しないので、この連鎖は最初の一歩で切れている。** 署名が要るのはアプリとインストーラーだけで、それは手持ちの OV 証明書でできる。

**したがって配布を妨げるものは残っていない。** 当初「(1) が主で (2) は従」と書いたのは正しく、主たる理由が従たる理由を無効にした形になる。

この改定により次が変わる。

| 項目 | 変更 |
|---|---|
| 自作仮想デバイスドライバ(`driver/`)の使用 | **対象外のまま。** 理由 (1) は変わらない |
| N-07(導入・削除) | **ドライバを含めない形で実装済み。** インストーラーはアプリのみを導入する |
| N-08(ドライバの署名) | **対象外のまま。** ドライバを配布しないため。アプリとインストーラーの署名は別途行う |
| F-34(英語対応) | **必須に復帰し、実装済み** (2026-08-06) |

エンジン・DSP・GUI に関する要件は一切変わらない。

### 4.1.1 配布にあたっての制約

**VB-Cable は同梱しない。利用者が自分で導入する。**

VB-Cable は VB-Audio 社の製品であり、再配布には同社との合意が要る。AudioLens のインストーラーは **導入の有無を確認して知らせるだけ** で、ドライバ本体は含めない。この設計は個人利用を前提にしていた頃から変わっておらず、配布に切り替えても手を入れる必要がない。

**利用者側のライセンスは利用者と VB-Audio の間の問題である。** VB-Cable は個人利用が無償である一方、業務・商用利用には別途ライセンスが必要とされている。AudioLens はその条件を代行できないので、 **導入を案内する箇所で VB-Audio の配布元へ誘導し、条件は各自で確認してもらう。**

> 上記のライセンス条件は 2026-08 時点の理解であり、一次情報は <https://vb-audio.com/Cable/> である。配布を始める前に現行の条件を確認すること。

**SmartScreen は当面警告を出す。** 手持ちの証明書は OV であり、EV と違って評価が即座には得られない。ダウンロード数が積み上がるまで「発行元不明」の警告が出る可能性が高い。これは署名の不備ではなく OV の性質である。

### 4.2 音声取り込み手段

- 音声取り込みは仮想オーディオデバイス方式を採用する(選定理由は `architecture.md` 参照)。
- **仮想デバイスには VB-Cable 等の既存ドライバを使う。同梱はしない** (§4.1.1)。M1 で「開発フェーズの割り切り」としていた構成が、そのまま最終形になる。
- 自作ドライバ(`driver/`)は開発成果の記録として残すが、ビルドも実行もしない。
- 仮想デバイスドライバの導入に管理者権限が必要となる。
- DRM 保護された一部コンテンツや排他モード(WASAPI exclusive)再生アプリは、仮想デバイス経由では音が取れない場合がある。制限事項としてユーザーに提示する。
- 開発言語は C++(C++20)。理由: WASAPI/COM とのネイティブ親和性、低遅延リアルタイム処理、ドライバ関連コードとの整合。

### 5.1 基準 3 を「定常状態」で定義する理由

曲送りなど音源側がストリームを畳んで張り直す瞬間、キャプチャへのパケット供給が一度途切れ、再開時に遅れて届く。リングバッファの充填はそのぶん一時的に増え、エンドツーエンド遅延も同じだけ増える。

これは AudioLens が作る現象ではなく、通常の再生操作で必ず起きる。そして **それを吸収することがリングバッファの役目** である。外乱は音切れで払うか遅延で飲むかのどちらかで、N-01(音切れを起こさない)を最優先する以上、飲むほうを選ぶ。リングを外乱吸収に足る大きさに保ったまま瞬間値まで 100 ms に収めることは両立しない。

したがって上限は定常状態に対して課し、過渡については「容量内に収まり、目標充填へ復帰すること」を条件とする。
